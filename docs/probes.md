## Graph and seed

  profile (not cross-origin isolated, no `SharedArrayBuffer`) the web app made it in-memory

  page. The import creates real user properties and tags with random ident suffixes

  It is not the UI's click path; values are stored the same way.
  - `#Project`: Start, End (Date), built-in Status, Owner (choice: Alice, Bob).
  - `#Client project` extends `#Project`, own property Client (text).
  - `#Meeting`: Date (DateTime), Type (choice: Planning, Review, 1:1).
  - Page `Planner probe`: projects Website relaunch (start −10 d, end +20 d), Mobile app (start only),

## How to re-run

```sh
# web app on :3001 with the dev plugin registered on plugin-test (or Demo), playwright-cli session open
PLANNER_PW_CWD=<playwright-cli session dir> npm run probe -- [--seed] [--writes] [--other-window]
```

`scripts/probe.mjs` evaluates in the host page through playwright-cli and calls the SDK *inside the
plugin iframe* through the dev-only hook `src/dev-probe.ts` (loaded behind `import.meta.env.DEV`,
absent from `npm run build`), so every fixture is what the plugin receives over the SDK bridge. It
refuses any graph other than `plugin-test` or `Demo`. `--writes` restores the seed values and deletes
the plugin property it creates; after the run no `plugin.*` ident is left (`writes.json` →
`cleanup.pluginIdentsLeft: []`).

## Open questions (REQUIREMENTS.md)

### Does `DB.onChanged` fire for changes from sync and other windows?

- **Local edit — observed: yes.** One payload per save: `{ blocks, deletedBlockUuids: [], txData: [],
  txMeta: { clientId, outlinerOp: "save-block" } }`.
- **Other window — observed: yes.** A second tab of the same browser on the same graph (the web app
  shares the db worker between tabs) edited a block with `update_block`; the plugin in the first tab
  received one payload with `txMeta.clientId` of the *second* tab (`64a58504…` vs this tab's
  `e2dc492a…`). Not tested: a second desktop window (Electron).
- **Plugin's own writes — observed: yes**, one payload per `upsertBlockProperty` /
  `removeBlockProperty`, `outlinerOp: "set-block-properties"`, with this tab's `clientId`.
- **Undo / Redo — observed: yes**, `txMeta` is `{ outlinerOp: "set-block-properties" }` with **no
  `clientId`**.
- **Sync — not tested**: the graph is local and in-memory, no account, no server. Source
  (`frontend/modules/outliner/pipeline.cljs`, `invoke-hooks`): the hook is published for every
  change delta of the *current* repo whatever its origin, except while importing, during initial
  page load, or when a delta has more than 1000 blocks. Not observed for sync.

### Exact API shape of class properties, inherited properties and closed values

Observed (`tags.json`, `class-properties.json`; pull-map keys keep their namespace except
`:block/*` and `:db/*`, which come back bare: `id`, `ident`, `uuid`, `title`, `cardinality`):

- A tag is `[?t :block/tags :logseq.class/Tag]`. Parent tags: `:logseq.property.class/extends`
  (a list; every tag without a user parent extends `:logseq.class/Root` "Root Tag").
  Client project → `[{ id: 223, ident: ":user.class/Project-…", title: "Project" }]`.
- **Own** properties: `:logseq.property.class/properties` on the tag. **Inherited properties are not
  materialised**: Client project lists only Client; Start, End, Status, Owner must be collected by
  walking `extends`. Built-in properties (Status) appear in the same list as user ones; order is not
  the order they were added.
- Property: `ident`, `title`, `":logseq.property/type"` (`"date"`, `"datetime"`, `"default"`, `"node"`
  … bare string), `cardinality` (`":db.cardinality/one"`, with colon), `":logseq.property/built-in?"`,
  `":logseq.property/public?"`.
- A **choice property** is type `"default"` with closed values. Closed values are separate entities
  pointing at the property: pull them as `{:block/_closed-value-property [...]}` → key
  `_closed-value-property`, each `{ id, uuid, title, order }` (+ `ident` and `":logseq.property/icon"`
  for built-ins). User choices have no ident.
- Built-in Status values: Backlog, Todo, Doing, **"In Review"** (capital R), Done, Canceled
  (`:logseq.property/status.<backlog|todo|doing|in-review|done|canceled>`). Only Todo
  (`":logseq.property/choice-checkbox-state": false`) and Done (`true`) carry the checkbox flag;
  **Canceled has no flag** — identify it by ident.
- SDK: `getTag(title)` returns **null** for every tag, built-in Task included; `getTag(uuid)` and
  `getTag(ident)` work. `getTagObjects(title)` rejects with `Not a tag`; by uuid or ident it returns
  the tag's nodes **including extending tags' nodes** (Acme rollout). `getTagsByName("Project")`
  works. `getAllTags()` lists 13 tags (built-ins + user); its `":logseq.property.class/extends"` /
  `/properties` are bare entity ids.

### Does a closed-value write via `upsertBlockProperty` work for user choice properties and built-in Status alike, and does Undo revert it?

Observed (`writes.json`). `upsertBlockProperty` resolved `null` in every case below — success and
failure look the same, so **always read back**.

| Key passed | Value passed | Built-in Status | User choice (Owner) |
|---|---|---|---|
| full ident (`"logseq.property/status"`, `"user.property/owner-…"`) | closed value entity **id** (number) | ✅ set | ✅ set |
| full ident | closed value **title** (`"Done"`, `"Bob"`) | ✅ set | ✅ set |
| full ident | closed value **uuid** string | ❌ silently set to `:logseq.property/empty-placeholder` | ❌ value silently gone |
| full ident | ident string `":logseq.property/status.canceled"` | ❌ empty placeholder | — |
| unqualified `"status"` | id | ❌ creates a plugin property `:plugin.property.<id>/status` (number) on the block; the real Status is untouched; resolves with a serialized cljs map | — |

- **Undo — observed: yes, for both.** Escape then ⌘Z in the host reverted the last plugin write
  (Status Doing → Todo; Owner Bob → the previous state), ⌘⇧Z redid it. Plugin writes go on the
  host's undo stack like user edits.
- `removeBlockProperty(uuid, fullIdent)` removes the value (Kanban "No <prop>" drop works this way).
- `removeProperty("status")` deletes the plugin property the unqualified write created.

## Other shapes (observed)

- **Tagged nodes** (`nodes.json`, `pull [*]`): user property values come back under full ident keys
  as refs `{ id }` (`":user.property/start-…": { id: 199 }`); built-in Status as
  `":logseq.property/status": { id: 78 }`; `tags: [{ id }]`, `page`, `parent`, `refs: [{ id }]`.
  Resolve refs with a nested pull or a second query.
- **Text property values are entities too**: Client "Acme" is entity 227 with its own uuid and
  title, and like every property value block it has a `:block/page`.
- **Date vs DateTime** (`dates.json`): a Date property value is a ref to a journal page
  (`journal-day: 20261008`, uuid `00000001-2026-1008-…`, title "Oct 8th, 2026"); a DateTime value
  is a bare epoch-ms number (`":user.property/date-…": 1791041400000` = today 10:30 local). Built-in
  Deadline and Scheduled are DateTime. The built-in "Node created at" / "Node updated at" are also
  `datetime`: take date properties from the tag's (own + inherited) class properties, not from
  "all properties of type datetime".
- **Task refs** (`tasks.json`): `:block/refs` of a task holds the linked node (inline `[[uuid]]` *and*
  a node-property value both land there), plus the Tags property, Status, Deadline/Scheduled
  properties and the Task tag. The `[?task :block/refs ?n]` join over the tag's nodes (with
  `class-extends` rules passed as a string input with a leading space) returned exactly the five
  expected (node, task) pairs. `:block/title` keeps `[[uuid]]`; the pull key `full-title` has the
  readable "Draft brief [[Website relaunch]]".
- **`getBlock`** (`sdk-blocks.json`): properties appear twice, at top level and under `properties`,
  keyed by full ident; ref values are expanded objects (`{ id, uuid, title, ident, journalDay … }`,
  camelCase); DateTime stays a number. `getBlockProperties` flattens values to titles
  (`"Sep 23rd, 2026"`, `"Alice"`), losing ids.
- **`onChanged` blocks** (all `onchanged-*.json`): camelCased, namespace-less keys. Built-ins become
  `status`, `deadline`; **user property keys are mangled** (`:user.property/start-Sd0PMVjj` →
  `startSd0PmVjj`, `:user.property/owner-rDOlrnNh` → `ownerRDOlrnNh`), so they cannot be mapped back
  to idents. `txData` is always `[]` (source: hard-coded in `publish-plugin-hook!`). A write to a
  node also lists the blocks that reference it (the three tasks linking Website relaunch), and a
  Status write lists property-history entities with no title.

## Consequences for later tasks

- **T03 schema**: list tags with a datascript query, not `getTag(title)`; walk
  `:logseq.property.class/extends` to collect inherited properties (Root excluded); choice =
  `"default"` + `_closed-value-property`; done set for Status from idents
  (`status.done`, `status.canceled`), not from the checkbox flag alone.
- **T04 queries/normalise**: Date = journal ref → `journal-day` (local calendar day, no time zone
  math); DateTime = ms → local ISO day + HH:MM. Tasks via `[?task :block/refs ?n]` restricted to
  the tag's nodes covers both inline refs and node properties.
- **T05**: Canceled is recognisable only by ident `:logseq.property/status.canceled` (or title for
  user choices).
- **T06 saved views**: properties written with an unqualified key land in the plugin namespace
  (`:plugin.property.<id>/…`, id random in dev); that is the intended path for plugin state.
- **T11 Kanban moves** (tasks.md numbering; Kanban is T11): write with the **full ident** and the
  **closed value's entity id**; never pass its uuid. Read back after the write, since failures
  resolve `null` too. Remove with `removeBlockProperty(uuid, fullIdent)`. ⌘Z undoes a move.
- **T12 live updates**: use `onChanged` only as a wake-up and re-query (payload keys are mangled,
  `txData` empty). It fires for the plugin's own writes and for undo; `clientId` tells another tab
  from this one but not the plugin from the user, and undo carries none.
